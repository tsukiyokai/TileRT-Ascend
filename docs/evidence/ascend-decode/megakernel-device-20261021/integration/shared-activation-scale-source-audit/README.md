# Captured shared SwiGLU scale contract

The original M32 shared activation reproduced all 4096 INT8 codes and 32 FP32 scales in one isolated call. The actual launch is `DequantSwigluQuant_int32_high_performance_30013`, with 12 vector blocks and 80 bytes of tiling. This is the legacy performance family despite the public call carrying `swiglu_mode=1`, `clamp_limit=0`, `glu_alpha=1` and `glu_bias=0`. [The log excerpt](dispatch-excerpt.txt) records those attributes, the selected key and the launched symbol; [audit.json](audit.json) records provider, source and binary identities.

Installed `dequant_swiglu_quant.cpp:304–310` maps key 30013 to `DequantSwigluQuantDynamicPerformance<int32_t, float, float, int8_t, 1, 0>`. Its `dequant_swiglu_quant_dynamic_performance.hpp:309–358` converts the INT32 accumulator, multiplies channel scale and then token scale, computes `gate / (1 + Exp(-gate))`, and multiplies by the up half. Lines 368–389 reduce the complete row, divide the scalar maximum by 127, use reciprocal multiplication to produce codes, and cast FP32 → INT16 with RINT → FP16 with CAST_NONE → INT8 with CAST_NONE. A zero scale selects reciprocal factor 1. The installed header and binary hashes match on a3-78 and a3-194. The 80-byte layout decoding uses the separately identified repository schema; the key, size and block count are direct log observations.

The existing native grouped path instead multiplies the maximum by the stored FP32 reciprocal of 127, divides activation by the broadcast scale, and casts through INT32. Changing only the emitted scale would leave a different code-generation contract. The captured codes happen to match. Constructed FP32 witnesses in [result.json](result.json) show reciprocal multiplication and division can round to different integer codes even with the same scale: for scale bits `3cf43e45` and activation bits `3c743e46`, direct division rounds to code 1 while multiplication by the rounded reciprocal rounds to code 0. These witnesses are exact CPU arithmetic examples, not captured device activations.

Captured GU accumulators have maximum magnitude 47793, so their INT32 → FP32 conversion is exact. The first retained discrepancy is scale at rows 0, 1 and 20, each one ULP lower in native. Under the native FP32 RNE multiply contract, each of all 32 scales has exactly one positive finite FP32 maximum preimage. Dividing those same inferred maxima by 127 reproduces every official scale, including the three discrepancies. The integer/Fraction implementation in [analyze.py](analyze.py) establishes uniqueness across the complete positive finite FP32 domain and rounds rational values directly to FP32.

These maxima were inferred, not captured. CPU Exp/division reproduces 29 of the 32 inferred maxima; rows 14, 20 and 29 differ, so the CPU activation is not an Ascend vector oracle. The selected legacy source and the scale counterfactual support correcting the complete activation quantizer, followed by all-boundary device validation. They do not establish a universal rule for other shapes, attributes or operator packages.
