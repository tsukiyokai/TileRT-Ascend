The release publisher is equivalent to `all_positive_counts<=16 || (sum=256 && max<=32 && active>=64 && 8*hot<=active)`, where `hot` counts experts above16 rows. The old branch is preserved. Valid COUNT input satisfies `sum(counts)=m`; the added sum test does not independently validate the input tensor shape.

Expert IDs, cumulative ends and padding are unchanged. `source-diff.json` verifies that all source outside `Publish`, including shape/template guards, synchronization, Matmul and epilogue, is byte-identical to the previous adaptive release.

`prepare.py` extracts that exact C++ `Publish` method, compiles it with small CPU storage stubs and executes18 cases in0.45s. The cases include the eight measured boundary count vectors, old small-group inputs, active63/64 with seven hot experts, sum255/256, max32/33, and same-active64 H8→H9→H8 reset. Counts and metadata retain the same addresses; each publication starts with poisoned metadata. Checks cover the complete header, every packed `(expert,cumulative_end)`, zero padding and untouched end guard. `result.json`, `publisher.cpp` and `cases.json` bind source and inputs. Stubbed pipe events do not validate asynchronous device or Graph behavior.

No floating-point computation is added by the guard. Wide/narrow arithmetic retains its existing contract and needs the release's actual MSD comparison. The 1/8 bound limits logical extra weight passes; measured active32 regressions show that it does not independently establish speed. The active64 condition is an empirical boundary from the current screen, not a universal performance guarantee.
